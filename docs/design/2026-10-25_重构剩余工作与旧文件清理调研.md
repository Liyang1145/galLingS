## 1. 结论

1. **新本体已具备内容构建、唯一 TypeScript 核心、共享游玩、正式记录配置和两端宿主代码；Windows 已实际编译出包含剧情和素材的应用。** 不能再说 Windows 只是空入口或“尚未出 EXE”。
2. **还不能说“除存档、回退、异常退出之外全部完成”。** 作者源切换与整仓清理仍未做完；新版本未启动试玩，类型检查/逻辑测试及全路线验收未执行；Android 尚未构建。安装分发、编辑器及正式聊天另有独立缺口。
3. **存档、回退和正常退出并非完全没写。** 已有新 TS 实现及接线；后置的是其体验扩展、正式规则和异常恢复。它们不需要旧播放器，也不是永久保留旧解释器的理由。
4. **旧运行实现对新本体已无必要。** 但同一个文件可能仍被旧制作导出、旧托管页面或旧聊天服务消费。因此要区分“新本体不需要”和“当前仓库可以单独删除”。
5. **`game.js` 仍是实际作者源，不是已无用的旧引擎。** 当前转成了发行数据，尚未迁成新的唯一作者源。可在切换读取/写回入口后退役其旧文件形式，不必永久保留，也不能现在直接删。

## 4. 为什么 `game.js` 还没有退出

当前实际链路：

```text
海风与布丁/game.js（唯一剧情、资源目录及设置输入）
  → tools/content/build.ts：loadSourceContent / compileSourceContent
  → tools/content/legacy.ts：严格解析与转换，不执行 JS
  → packages/story-model 的规范化数据
  → tools/game/build.ts：写 content/story.json、复制素材
  → 新 TS 核心与表现，Windows/Android 宿主
```

游戏开发入口、终端试播和已有独立编辑 API 仍使用同一读取/转换链。根 `content/game-ui/` 仅拆出了鲸鱼图形和图标；`docs/rebuild/baseline/` 只记录固定身份，二者都不是完整剧情源。`dist/game/.../content/story.json` 是生成物，不是已采用的新作者文件。

因此，**已拆的是运行职责和部分 UI 资源，尚未完成作者源切换**。替换源文件形式应当保留：

- 全部 3315 节点，包括不属于正常开局的前两个节点；原节点/选项/资源身份及数组顺序。
- 变量初值、条件/动作、章节/结局、限时默认项、音乐继续/停奏及作者设置/来源元数据。
- 当前 `choices.json` 的稳定选项身份；不能在新格式里重新按文字或位置分配。
- 共享构建/开发/预览读取，以及现有受限写回能力的明确去向；不长期双写。
- 源切换对内容修订、来源定位、已有新检查点及编辑补丁的实际影响；没有旧存档不代表新版本校验可以移除。

这里没有确定新源一定采用单文件 JSON、按章节拆文件或其他结构。正式实施前应在具体切片里明确这个选择；不用为此先把整个编辑器重构完，但不能悄悄留下写回旧文件的第二条作者链。

## 6. 后续实施边界与建议顺序

建议先围绕 **R1 作者源切换与 R2 旧链路退出** 做下一片具体收尾，解决“新应用已经能构建，为何仓库还保留旧数据包装和制作模板”的真实缺口。此顺序是建议，尚未决定替代作者格式，也没有废弃旧完整制作或聊天的产品决定。

每组清理可用以下标准判断完成：

1. 明确新本体不再使用的文件，以及仍保留的具体旧功能。
2. 若要退役该旧功能，连同调用入口、依赖、专属测试/工具说明成组处理；不留下断开的可点击入口。
3. 作者源/资源先接好实际新消费者，保持单一来源，再删旧载体；只移除 JS 包装不冒充完成结构化作者模型。
4. 记录语义/格式/内容修订影响和待验证项，小步中文提交；保留他人改动，不重写历史。
5. 需要验证时按用户安排开展，不能用本文中的清单自动授权测试、构建、试玩或 CI。

Windows 应用可以由用户另行安排试用，实际反馈可直接成为下一片修复输入。Android 首次构建另按明确安排开展；存档扩展、回退规则、异常退出恢复和编辑器继续后置，主线不等待聊天。
