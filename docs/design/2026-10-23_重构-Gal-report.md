## 1. 执行摘要

项目的问题不只是 JavaScript 缺少类型，而是作品内容、剧情解释、演出、编辑工具、平台封装和 Agent 能力的职责交叉，且存在不止一条剧情执行路径。仓库已经有导入器、Rust 核心、宿主、插件和测试等工程成果，不能简单认定为“什么工程化都没有”；真正需要重建的是围绕游戏交付的组织方式和运行契约。

建议采用 **TypeScript 自研游戏运行体系**：建立唯一的剧情核心，把现有有价值的画面和声音实现迁到清晰模块中，用内容构建连接编辑器与游戏，Windows 和 Android 共享同一套主线逻辑。编辑器独立发布，预览复用同一运行实现；通关后角色聊天独立接入，不成为主线启动和游玩的前提。

这不是把所有文件改成 `.ts`，也不是先建设通用引擎。重构主线是：**重建核心、转换内容、迁移演出、接好存档与平台、拆出编辑器、隔离聊天**。迁移期间保留可发布的旧版和独立的新版本，禁止在一次游玩中遇错就从一种剧情解释器切换到另一种。

建议先完成“内容语义清单与转换”，再完成一条包含变量、选择、存读档、音频和前后台切换的纵向切片。只有这条链路能正确工作，才推广到全部作品内容；聊天不阻塞离线游戏本体交付。

**工程化 `AGENTS.md` 是本次重构的正式交付项，不是收尾时补写的说明。** 它需要在多人进入新工程前提供可靠协作入口，并随着真实目录、接口和命令落地持续更新；现有混乱规则不能原样搬进新入口。本轮只把这项工作写入计划，不修改现有 `AGENTS.md`。

## 2. 决策状态：什么已确定，什么还没有

### 2.1 用户已经确认

| 项目 | 已确认内容 | 对重构的约束 |

### 2.2 本文提出的架构建议

下列建议有明确理由，但不伪装成用户已经逐项批准：

- 一个仓库组织游戏应用、编辑器应用和共享模块；独立构建和交付，不是微服务拆分。

- TypeScript 开启严格检查；构建工具与包管理采用成熟方案，而不是自研这些基础设施。
- 一次性选择、限时选择、存档恢复、回退和播放取消先定义语义，再迁移界面。

## 3. 重构范围与不做的事

### 3.1 本次计划覆盖

1. 游戏代码的组织方式、类型契约和依赖方向。
2. 作品内容从编辑态到发行态的转换。
3. 唯一剧情核心、游戏会话和演出之间的职责划分。
4. 变量、条件、选择、限时、回退、存档及恢复的准确语义。
5. 离线主线与 Windows、Android 的平台适配。
6. 编辑器独立及预览复用。
7. 通关后角色聊天的最小接入位置。
8. 旧实现退出路径、迁移阶段和未来验收依据。
9. 工程化 `AGENTS.md` 的内容规格、作用范围、落地阶段、维护责任和验收条件。

### 3.2 不作为重构前置

- 通用脚本语言、完整插件市场、任意用户 Mod 系统。
- 自研 UI 框架、包管理器、构建器、依赖注入容器或跨端通信框架。
- 通用 Agent 调度、任意工具执行、浏览器控制和全套 MCP 平台。
- 聊天内容反向改写主线剧情。
- 以清理仓库为名重做美术、音乐、文本或剧情设计。
- 为统一语言立即删除全部 Rust、Python、Java 代码。
- 为目录整洁改写 Git 历史、整库搬迁、去除素材来源或删除所有“归档”。
- 现在承诺旧存档百分之百兼容、具体发售日期、精确工期或依赖版本。

**“继续自研”的范围是游戏规则、运行编排和作品工具，不是从零重做所有通用基础能力。**

## 5. 目标结构：两个应用，一套主线运行实现

### 5.1 总体关系

以下是目标关系示意，不代表当前目录或实现已经存在：

```text
制作人员
  → 独立编辑器
      → 可编辑作品源
      → 内容构建与资源清单
          → 可发行内容

玩家 → Windows / Android 宿主
          → 游戏应用
              → 游戏会话
                  → 唯一剧情核心
                  → 表现模块
                  → 存档与玩家记录
                  → 平台适配器

编辑器预览 → 复用游戏会话、剧情核心和表现模块
通关事实 → 只读通关上下文 → 独立角色聊天模块 → 联网能力
```

“共享”指同一源实现及同一内容语义，不要求两个原生安装包字节相同，也不要求两端共用同一原生宿主代码。

### 5.2 模块职责与状态归属

| 模块 | 唯一负责的内容 | 不应负责 |
|---|---|---|
| 剧情核心 | 当前节点、剧情变量、条件、有效选项、流转、结局、逻辑快照 | DOM、音频对象、网络、文件位置、模型请求 |
| 游戏会话 | 串行接收操作，协调剧情、演出、暂停、取消、检查点和恢复 | 自行计算另一套选项条件或变量变化 |
| 表现模块 | 画面、文字、转场、立绘、音频及其播放句柄 | 更改剧情变量、决定结局、直接推进到任意节点 |
| 存档模块 | 存档封装、格式版本、校验、兼容处理、可靠持久化 | 根据屏幕内容推测剧情状态 |
| 玩家记录模块 | 已读、解锁、必要的跨局事实及其写入规则 | 代替当前进度快照 |
| 平台适配器 | 文件落点、宿主生命周期、返回键、窗口、平台桥接 | Windows 或 Android 专属剧情规则 |
| 内容构建模块 | 读源内容、检查、规范化、转换、资源映射与发行清单 | 播放剧情、携带编辑器状态进入游戏 |
| 编辑器 | 内容编辑、诊断、预览入口、导入和导出 | 另一套正式剧情解释器 |
| 角色聊天模块 | 对话会话、请求状态、联网错误、聊天记录 | 任意更改主线变量、回退历史或结局记录 |

每个模块都应隐藏一段真实复杂度，而不是只给另一个同名对象转发调用。不要把今天的全局对象换成一个拥有数百个方法的 `GameManager`。

### 5.3 依赖规则

- 剧情核心只依赖作品模型和必要的纯计算，不依赖游戏应用、编辑器或宿主。
- 游戏会话使用剧情核心、表现和存储接口；界面通过游戏会话操作剧情。
- 表现模块可以依赖 Web 渲染能力，但不依赖编辑器。
- 编辑器预览依赖共享播放器，不从游戏应用中反向导入内部页面。
- 平台差异在真实接缝处用适配器实现，不把每个纯函数都抽象成接口。
- 聊天只能通过只读通关上下文接触主线信息；聊天模块的异常不能中断游戏启动。
- 游戏发行物不得包含编辑器应用、作者工作目录、开发后端或素材归档。

## 6. 内容协议：先明确作品是什么，再重写解释器

### 6.1 三类内容及唯一来源

| 类型 | 用途 | 可否人工编辑 | 去向 |
|---|---|---|---|
| 作者源内容 | 日常制作的权威内容 | 可以，由编辑器或约定的数据工具修改 | 版本管理和内容构建 |
| 规范化发行内容 | 核心直接消费的确定格式 | 不手改，通过构建生成 | 游戏安装包和编辑器预览 |
| 旧格式基线 | 迁移与对照依据 | 切换后只读 | 可追溯保留，不再作为第二个写入源 |

迁移初期可以继续以当前作品数据为输入；切换后只能有一个权威可编辑源。不能要求制作人员长期同时维护旧 `game.js`、新 JSON 和编辑器私有工程三份剧情。

作者源格式是否与发行格式相同，可以在编辑器选型时决定。**允许有不同格式，不允许同一份业务内容有互不受控的多个权威来源。**

### 6.2 一个剧情节点的四部分

| 部分 | 内容 | 执行或使用时机 |
|---|---|---|
| 进入动作 | 变量赋值、增减等当前节点的剧情变化 | 真正进入节点时执行一次 |
| 呈现内容 | 说话人、对白、目标场景、语音引用 | 每次展示或恢复该位置时使用 |
| 演出指令 | 转场、角色动作、一次性音效 | 正常进入时按规则播放，恢复时区别处理 |
| 流转规则 | 顺序、选项、条件跳转、结束 | 当前交互条件满足后由核心执行 |

核心规则：**恢复不是重新进入。** 从存档恢复一个已经执行过进入动作的节点，不能再执行一次好感增加，也不能把恢复当成“再次达成结局”。

### 6.3 最小内容字段及约束

以下字段名是拟议名称，正式 Schema 在实施第一阶段确定：

| 对象 | 必需信息 | 约束 |
|---|---|---|
| 作品 | 作品 ID、格式版本、内容修订、入口节点、变量定义、节点及资源清单 | 缺失关键引用必须明确报错 |
| 节点 | 稳定节点 ID、来源定位、进入动作、呈现、演出、流转 | 不以数组下标作为长期身份 |
| 变量 | 稳定标识、显示名、类型、初始值、允许写入范围 | 初始值及操作经过显式转换，不靠 JS 隐式强转 |
| 选项 | 稳定选项 ID、文字、条件、动作、目标 | 显示文字和排列位置不能充当身份 |
| 限时选择 | 有效时长、超时策略、可定位的默认选项或去向 | 超时行为不隐含为“选第一项” |
| 场景 | 完整背景、角色状态、持续音轨及必要布局 | 区分清空、停止、继续与未设置 |
| 演出 | 指令种类、目标、参数、等待和取消规则 | 不支持的指令不能静默丢弃 |
| 资源 | 稳定资源 ID、种类、发行位置、校验信息、来源信息 | 不把机器绝对路径写入发行内容 |

当前节点和资源 ID 默认保留，转换过程提供旧字段到新字段的映射。旧选项没有稳定 ID 时，由迁移工具一次性分配并保存映射；不能每次依据当前文本或排序重新生成。

### 6.4 表达式与变量

- 保留作品实际需要的数值、布尔和字符串语义；不要因为旧 Python 导入器只接受部分整数表达式，就把它当作完整规格。
- 作者可以使用受限的文本表达式，构建时解析成受限结构；发行运行时不执行 `eval`、动态函数或任意脚本。
- 变量修改应明确支持哪些赋值与运算，条件应明确支持哪些比较和逻辑组合。
- 未声明变量、类型不匹配、除零等非法行为需要明确规则和定位信息，不默认为零继续运行。
- 当前声明变量的初始值是字符串形式的 `"0"`；转成数值是迁移转换行为，需要显式记录，不能偷偷混用。
- 当前播放器支持跨局变量及周目、结局数等只读信息。迁移要区分剧情变量、可写跨局状态和只读玩家记录投影，不能简单把所有变量塞进同一个可写字典。
- 剧情核心通过显式输入获得必要的玩家记录投影，不直接读存储。读档、回退和新周目何时刷新该投影，需要在语义清单中逐项规定。

### 6.5 选择与流转的精确次序

建议采用以下次序，并以转换对照确认是否存在作品特例：

1. 进入节点，执行进入动作。
2. 基于执行后的状态计算展示和可用选项。
3. 玩家选择或超时确定一项有效结果。
4. 一次性执行该选项的动作。
5. 求得目标节点，再进入目标节点。

补充约束：

- 条件隐藏和不可点击是不同表现，内容格式必须能表达作品需要的那一种。
- 全部选项被条件隐藏时，必须有明确去向或构建诊断，不能出现空菜单死锁。
- 普通跳转、条件跳转与结局必须有明确优先级；同一节点出现冲突字段时由构建报告，而不是由字段读取顺序碰运气。
- 自动播放、快进和手机返回键不能绕过核心的选择结算规则。
- 允许剧情形成循环，但不能让没有交互或可等待点的无条件循环卡死运行；构建尽可能诊断，运行仍有保护。

### 6.6 场景描述不等于演出过程

目标场景描述“最后应该是什么”，演出指令描述“如何到达那里”：

- 背景、立绘、持续 BGM 和环境声属于目标场景。
- 淡入、摇动、镜头动作、一次性音效属于演出过程。
- 没有 BGM 与继续当前 BGM 必须可区分；停奏是作品内容，不是可忽略的空值。
- 同一个音频文件继续播放还是重新开始，不能只按资源 ID 判断；要有明确的连续播放或重启语义。
- 恢复目标场景时不默认重播一次性音效。

如果作者格式允许继承上一场面，规范化时必须考虑真实流转路径；不能仅按节点数组的上一项展开，因为节点可能被分支和跳转进入。优先让发行节点具有完整目标场景；确实需要路径相关场景时，显式记录其状态并进入快照，而不是偷偷依赖 DOM 残留。

## 7. 剧情核心接口：小接口，完整语义

### 7.1 拟议接口

以下是讨论用接口片段，不是已经实现或编译的代码。相关类型的职责在紧随其后的表中定义，正式字段名允许在实现切片中调整：

```typescript
interface StoryRuntime {
  view(): RuntimeView;
  dispatch(command: RuntimeCommand): RuntimeResult;
  snapshot(): StorySnapshot;
  restore(snapshot: StorySnapshot): RestoreResult;
}
```

| 类型 | 应包含什么 | 不应包含什么 |
|---|---|---|
| `RuntimeView` | 当前节点、对白引用、目标场景、有效选项、逻辑阶段、当前步骤标识 | DOM、`Audio`、计时器句柄 |
| `RuntimeCommand` | 请求继续、按选项 ID 选择、当前演出完成、选择超时；携带对应步骤标识 | 任意写变量、按数组索引强行跳转 |
| `RuntimeResult` | 是否接受、本次状态、表现要求、本次新发生的事实或明确错误 | 自动发网络请求或写文件 |
| `StorySnapshot` | 可恢复的剧情位置、已生效变量、流转上下文和版本识别 | 正在运行的回调、宿主对象、聊天凭据 |
| `RestoreResult` | 恢复成功后的视图，或格式、修订、节点及状态不兼容原因 | 失败后悄悄用旧下标继续 |

输入内容、初始玩家记录投影及必要的确定性配置通过创建运行实例时提供。核心不主动读取时钟；选择超时是游戏会话依据有效计时发送的显式输入。

只读玩家记录投影变化的接收方式属于正式接口细化项：必须显式、可追踪，不允许核心在任意求值时查询全局存储。

### 7.2 输出分三类，不能混用

| 输出 | 含义 | 重复读取时的行为 |
|---|---|---|
| 状态描述 | 现在是什么，例如当前节点、变量和有效选项 | 可重复读取，不产生新事实 |
| 表现要求 | 当前应展示什么、需要完成哪些演出 | 可取消或恢复，遵守步骤标识 |
| 本次事实 | 这一次真正选择了某项、第一次进入了某个位置、达成了结局 | 只随已接受的状态转换产生，不由界面重渲染产生 |

状态订阅、界面重绘和读档恢复不能重复发送“增加结局数”。事实消费者需要幂等写入；这不是引入完整事件溯源系统的理由。

### 7.3 确定性与错误

在相同内容、初始状态和命令序列下，核心应得到相同的剧情结果。涉及时间或未来可能出现的随机行为，都需要通过显式输入处理，不能藏在内部环境读取中。

错误分两类：

- **可拒绝操作**：旧步骤回调、重复选择、当前不能继续等。保持状态不变，向会话返回明确原因。
- **内容或状态错误**：目标节点不存在、变量操作非法、快照不兼容等。保持可诊断状态，不切到另一套解释器，不用默认值掩盖。

`restore` 应先验证，再整体替换有效状态；失败不能留下“节点恢复了、变量没恢复”的半成品。

## 8. 游戏会话：处理点击、演出和计时之间的关系

### 8.1 逻辑阶段与表现阶段分开

逻辑阶段可表达：等待当前呈现完成、允许继续、等待选择、已结束。表现模块可同时拥有打字、语音、转场等播放状态，两者不是同一枚布尔值。

例如：

- 文字还在显示时，首次点击通常只补全文字，不向核心发送下一节点命令。
- 文字已显示不等于语音必然结束；自动播放按明确的等待规则继续。
- 选择出现时，自动播放不得替玩家作答，限时策略除外。
- 快进可以压缩演出，但不能略过变量动作、必需选择和结局事实。

上述默认体验仍需与现有作品对照，不能借重构名义静默改变。

### 8.2 统一操作入口与取消

会话对界面提供少量意图操作，例如继续、选择、暂停、恢复、存档、读档、回退和离开。按钮、键盘、自动播放、倒计时都进入同一个串行处理入口。

每次进入、读档、回退或重新开始都要有可区分的会话代次及步骤标识：

- 步骤标识用于判断“这份回调是否仍属于当前节点的当前进入”。
- 会话代次用于使读档之前的所有异步任务失效。
- 标识由会话协调并传递，核心只接受当前有效步骤的命令；不能使用系统墙钟作为唯一标识。
- 快照不复用运行中的旧回调身份；恢复后为可继续的工作分配新身份。

取消需要覆盖文字计时、选择计时、转场、音频回调及资源加载后的应用。底层不能真正取消的加载，完成后也必须通过代次判断，禁止覆盖新场面。

### 8.3 限时选择与竞态

选择由核心一次性结算。点击和超时即使几乎同时到达，也只能有一个有效结果：

1. 会话按串行顺序处理输入。
2. 核心检查步骤标识和当前选择是否仍开放。
3. 第一个合法结果执行选择动作及流转。
4. 后续结果因步骤或阶段不匹配被拒绝，不再次加值。

计时使用有效游玩时间，而不是简单比较保存时和当前的日期时间。打开菜单、切到后台或宿主暂停时，按作品确认的规则暂停；当前播放器已存在菜单及后台暂停处理，迁移时应保留，不默认让时间继续流逝。

存档保存剩余有效时间。读档不能把“还剩 3 秒”意外恢复为完整 15 秒，也不能因为离线放置一天立即视作超时。到期时仍需验证默认选项是否可用；内容必须明确失效后的策略。

### 8.4 真实节点的行为追踪

当前节点 `pm8x8v2h` 的对白是“来听春水第一声。”，包含 15 秒限时选择；其中“（沉默）”对应 `好感 += 8`，旧标签 `c5q2c` 对应节点 `3bu4bzeb`。当前数据的 `cdef` 也指向 `c5q2c`，即该项是现有超时默认结果。

它可以作为迁移对照样例：

| 操作 | 应保留的语义 |
|---|---|
| 正常选“（沉默）” | 执行一次 `好感 += 8`，再进入映射目标 |
| 按现有默认配置发生超时 | 选择“（沉默）”并结算一次，不额外执行第二次 |
| 点击与超时相邻到达 | 只接受一个结果 |
| 选择前存档后读取 | 恢复选择和保存的剩余时间，不提前修改好感 |
| 选择后保存、读取 | 好感不会因读取再次增加 8 |
| 从目标回退到选择前检查点 | 恢复对应进度状态，而不是“当前值减 8” |

这是一组依据现有内容提出的验收情景，不表示本轮已执行；如果要改变现有默认项，应作为独立内容改动。另一个限时节点 `3nnvr3w2` 也应进入内容迁移清单。

## 9. 演出与音频：迁移价值，不迁移全局耦合

### 9.1 应优先保留什么

现有 UI、角色布局、台词表现、音量控制、音轨恢复与一次性声音抑制都有价值。正确做法是提取实现，把输入改成明确的场景和演出要求，而不是为了复用继续向外暴露 `P`、`RT`、`stage` 等全局可写状态。

表现模块应围绕三类操作设计：

- 呈现场景与对白。
- 执行可等待、可取消的演出。
- 捕获和恢复必要的播放状态。

不必提前设计几十种抽象；只为当前作品的真实能力提供稳定接口。

### 9.2 不同声音分别处理

| 声音 | 正常流转 | 恢复时的建议 |
|---|---|---|
| BGM | 按内容决定继续、替换、渐变或停奏 | 恢复正确曲目和停奏状态；支持时恢复位置 |
| 持续环境声 | 按场景连续存在或停止 | 与目标场景一致，不能混入旧场景残留 |
| 当前对白语音 | 与该对白绑定，遵守等待和打断规则 | 重播、停止或尝试续播需确认体验 |
| 一次性动作音效 | 正常进入或指令触发时播放一次 | 默认不重放 |
| 交互提示音 | 与实际操作绑定 | 读档和重渲染不能自动触发 |

持续音轨不能仅按文件名比较。相同文件的“继续”和“重新播放”是不同意图；不同场景明确停奏后，不能因之前正在播放而遗留音乐。

### 9.3 不追求没有收益的帧级保存

首期建议保存“能正确恢复游玩”的状态，不保存动画引擎内部对象。过渡中存档可以先规范化为目标场景，恢复时直接呈现稳定结果；不承诺逐帧续接淡入和摇动。

如果某段演出影响何时允许选择或继续，必须保存对应等待语义或定义稳定恢复点，不能只恢复一张画面而让剧情处于另一阶段。

Android 上的内存、音频解码和前后台恢复需要真机观察；把文件改成 TypeScript 并不能解决这类问题。资源加载应按章节或邻近节点控制，不默认一次解码全部语音和图片。

## 10. 存档、读档、回退与玩家记录

### 10.1 四类记录要分开

| 记录 | 内容 | 是否随进度回退 |
|---|---|---|
| 剧情快照 | 当前节点、已生效变量、流转状态 | 是 |
| 会话恢复信息 | 必要的场景、展示阶段、选择剩余时间、播放恢复数据 | 随对应检查点 |
| 玩家记录 | 已读、解锁、周目及其他跨局事实 | 按明确产品规则，不直接整体覆盖 |
| 偏好设置 | 音量、文字速度、窗口与显示偏好 | 通常不随进度回退 |

存档模块封装前两类的一致快照。玩家记录和设置分别管理，不能为了方便把整个应用状态全部序列化。

### 10.2 一致检查点

一个可保存检查点应包含：

- 作品 ID、内容修订、存档格式版本。
- 当前节点 ID、已经生效的剧情状态和必要流转上下文。
- 目标场景，或足以无歧义重建目标场景的内容引用与路径状态。
- 当前展示与选择阶段、选择剩余有效时间。
- 按最终策略保存的语音与持续音轨恢复信息。
- 存档展示用的时间、摘要和可选缩略图。

**剧情快照和会话恢复信息必须来自同一个检查点。** 不允许先异步截屏，随后从已经推进到下一节点的变量中拼装存档。

缩略图失败不应破坏核心进度保存。写入失败时保留旧存档，给出可重试信息；不能先删除旧槽位再尝试写新数据。

不同存储适配器应提供等价的失败保护：文件可采用临时写入后替换，数据库可使用事务。具体机制在平台接入时选择，不能假定所有平台都支持同一种文件操作。

### 10.3 读档流程

建议的读取顺序：

1. 读取并校验存档封装、作品身份和版本兼容关系。
2. 预备新的剧情状态，确保节点、变量与恢复信息合法。
3. 取消旧会话任务，切换到新的会话代次。
4. 一次性采用新检查点，重建场景和必要播放状态。
5. 根据保存的阶段恢复操作，不重放进入动作或旧事实。

格式验证失败时保持原会话或回到可理解的菜单；不能部分采用损坏状态。采用新状态后如果某项媒体加载失败，应提供同一步骤的重试或明确降级，不能靠重新进入节点重试，否则变量可能再次变化。

### 10.4 回退不是逆向执行

进度回退恢复先前检查点，不把历史操作倒过来计算：

- `好感 += 8` 的逆操作并不总是简单 `好感 -= 8`，因为中间可能有赋值、分支和跨局副作用。
- 回退历史需要保存足够的状态，或使用能正确重建检查点的确定机制；首期不必建设通用事件溯源。
- 对白回看只是阅读记录，不应触发回退。
- 可回退范围、是否跨选择和结局、历史容量及退出后保留范围需要明确。
- 无论怎样定义，不能让无限检查点或大图缩略图占满 Android 内存。

### 10.5 玩家记录与事实写入

建议已读和结局解锁采用明确、幂等的记录方式；重复的界面刷新或恢复操作不形成第二次结算。周目、结局次数与可写跨局变量不能只套用集合合并，需要分别定义。

必要记录与检查点的持久化应有一致性策略：同一存储支持事务时一起提交；否则选择可重试、幂等的写入顺序。不要声称跨两个独立存储天然“恰好一次”。聊天解锁依赖的通关事实应可靠落盘后再显示为已解锁。

当前内容若读取周目或结局数，需明确在开始游玩、读档和回退时使用哪个投影。推荐把不受回退影响的成果与可回退剧情状态分开，但是否改变旧作语义必须作为显式产品决定。

### 10.6 旧存档兼容只作可选迁移

当前保存逻辑记录 `lineId`、数组下标和进入前变量；读档还存在按 ID 查找、找不到再用下标的行为。新结构不能直接把这些字段改名当成兼容完成。

如果决定支持旧存档，应提供一次性迁移器：

1. 识别支持的旧格式和来源内容基线。
2. 通过节点 ID 及明确映射定位。
3. 按旧存档“进入前变量”的语义计算新检查点。
4. 对缺失字段采用公开、有限的恢复策略。
5. 保留旧档备份，生成新档，不原地覆盖。

无法明确迁移时提示不兼容或允许玩家选择可靠的章节重开位置。**禁止按旧数组下标静默接着玩。** 是否投入这项工作仍待确认，不阻塞新核心设计。

## 11. 四种版本，不能混成一个数字

| 标识 | 代表什么 | 什么时候变化 |
|---|---|---|
| 内容格式版本 | 发行内容结构和字段语义 | Schema 或解释规则改变 |
| 内容修订 | 某一份确定的作品内容及资源引用 | 剧情、变量、节点、资源等发生变化 |
| 游戏发行版本 | 交付给玩家的软件版本 | 产品发布时 |
| 存档格式版本 | 存档封装及恢复状态结构 | 存储结构或恢复语义变化 |

资源可另有文件校验值，不能用安装包文件名替代内容身份。内容修订的计算应有规范化规则，避免仅因字段顺序不同就误认为一份新内容。

兼容判断至少检查作品身份、存档格式和内容修订。允许兼容修订时必须有显式规则或映射；“节点 ID 还在”不保证分支变量和场景仍兼容。

构建记录应能关联代码提交、内容修订和发行物校验值，以便定位问题。本文日期和示例字段不是给产品擅自分配版本号。

## 12. Windows、Android 与离线要求

### 12.1 共享什么，分别适配什么

| 共享部分 | 平台部分 |
|---|---|
| 规范化内容、剧情核心、会话语义、主要表现实现 | 本地资源访问方式 |
| 存档数据模型和兼容规则 | 存档实际落点及写入机制 |
| 选择、自动播放、快进和恢复行为 | 返回键、窗口、触控和键盘接入 |
| 通关后聊天规则和数据模型 | 前后台通知、系统音频及安全凭据存储 |

不必为了统一宿主而推迟唯一剧情核心。当前 Windows Tauri 与 Android WebView 可以先接入相同的前端发行物，再根据真实问题决定是否统一。

Tauri 的原生核心进程和 WebView 有不同职责，统一 TypeScript 业务逻辑不代表必须移除原生宿主。[R-04] Android WebView 同样需要宿主处理页面加载、导航及桥接等能力，不能把 Android 包当成一张无需管理的网页。[R-05]

### 12.2 离线主线的发行条件

- 必需剧情、图片、语音、音乐、字体和前端代码随本地内容安装。
- 首次进入主线不等待登录、模型可用性、远程配置、远程字体或 CDN。
- 主线不要求启动 Python 后端或联网服务；宿主本地资源协议不等于在线后端。
- 内容完整性异常给出本地诊断，不偷偷联网补齐来掩盖发行缺项。
- 关闭、拒绝或无法配置聊天，不影响主线按钮和存读档。
- 系统运行依赖也要进入分发考虑，例如 Windows 所需 WebView 运行环境；不能只在开发者机器上假定已安装，再让玩家离线时临时下载。
- “断网可玩”不等于承诺所有资源缺失时也可玩。安装完整性、系统要求及离线安装方式应在分发形式确定时写清楚。

### 12.3 生命周期契约

宿主暂停时，会话暂停有效计时与应暂停的播放；恢复时不重入节点、不自动补算后台的剧情时间。音频焦点、软键盘和返回键行为由平台适配器接入会话，而不是直接改剧情变量。

Android 进程可能被系统回收，不能只依赖“退出时保存”。建议在重要选择及稳定检查点安排可恢复记录；恢复到最近可靠点，不承诺继续任意被杀瞬间的动画帧。

最低 Android 版本、WebView 能力、方向锁定、屏幕安全区、Windows 最低环境和具体设备清单在平台切片时确定，本轮不虚构兼容保证。

## 13. 编辑器独立：共享内容和预览，不共享生产副作用

### 13.1 编辑器与游戏的关系

- 编辑器可以与游戏同仓库，但有独立入口、依赖和构建产物。
- 游戏发行物不加载编辑器脚本，不暴露素材写入入口。
- 编辑器读写作者源，通过同一内容构建得到可预览内容。
- 预览复用剧情核心、会话和表现实现，不维护编辑器专属的另一套解释器。
- 预览使用隔离的临时存档、玩家记录和聊天配置，不污染正式游玩记录。

预览从中间节点开始时，需要完整的初始变量和场景上下文。不能默认把变量清零，再把预览结果声称为“真实路线已验证”；编辑器应显示这是特定初始条件下的预览，或从已保存检查点启动。

### 13.2 不急着重写全部制作工具

先制定内容协议、转换器和预览接入，再决定：

1. 现有工具能否输出合格的作者源。
2. 现有美术编辑能力哪些可以保留。
3. 制作人员真正缺的是剧情图、资源管理、对白编辑还是演出预览。
4. 哪些操作需要稳定 ID、引用更新和诊断定位。

可以先独立现有工具并逐步替换。不能一边要求作者继续生产，一边无过渡地移除唯一能编辑现有作品的入口。

### 13.3 导入导出约束

编辑器往返保存后，要保留节点和资源身份、已知字段及可追溯来源。遇到不认识的扩展字段应保留或明确拒绝，不能打开再保存就无声丢数据。

对剧情 ID 的删除、资源替换和变量重命名，应提供引用影响信息。正式发行仍以构建诊断为准，不能只相信编辑器界面上的“保存成功”。

## 14. 通关后角色聊天：独立的联网玩法

### 14.1 最小结构

```text
主线达成结局
  → 可靠保存通关事实
  → 生成只读通关上下文
  → 解锁角色聊天入口
  → 聊天模块管理对话及联网请求
```

通关上下文可以包含作品身份、内容修订、结局 ID、必要的关系状态和作者设定引用。不要默认发送完整存档、所有历史选择或玩家本地资料。

“满足哪个结局才解锁”“多个通关记录用哪一个”“聊天是否接续某条具体路线”仍是产品细化项，接口应能区分上下文，不默认全混成一份记忆。

### 14.2 与主线隔离

- 聊天记录、请求状态和可选记忆不放入主线进度快照。
- 聊天获得只读通关上下文，不持有剧情核心的可写引用。
- 模型输出先作为聊天内容展示，不解析成主线任意指令。
- 首期不赋予模型文件操作、任意网络工具或宿主命令执行能力。
- 聊天离线、超时、额度不足、凭据错误时，显示聊天自己的错误与重试，主线仍可正常使用。
- 离开聊天或切换通关上下文时取消旧请求；旧流式回调不能写入新会话。

如果未来确实想让聊天改变游戏状态，应另立有限、可审计的动作协议和产品规则，不能以“Agent 功能”名义直接开放存档字典。

### 14.3 后端与隐私

模型供应和费用模式未定，因此本方案只定义能力接缝，不提前承诺“玩家自己填 Key”或“项目方统一代理”。

建议：

- 商业服务端凭据不放入游戏安装包、前端配置或公开仓库。
- 如果玩家自带凭据，使用适当的宿主存储并明确风险，不混入剧情导出或错误日志。
- 首次上传通关上下文前说明会发送什么。
- 明确超时、取消、流式重连与重复发送策略；不盲目自动重试造成重复计费。
- 长期记忆、远程保存、删除聊天记录和收费规则有真实需求后再设计。

现有 Python 后端、GalAgent 和插件可以作为能力来源评估，但不能因为它们存在就要求游戏启动时全部运行。

- 新核心尽量使用显式联合类型，不用 `any` 把外部输入一路透传。

- 禁止通过全局函数重定义、原型补丁或导出内部可写状态连接模块。
- 依赖从应用指向共享模块，不能循环，也不能让核心反向依赖应用。
- 资源和内容诊断携带作品、节点、字段与来源定位。
- 不建立没有实际消费者的 `shared/utils/common` 大杂烩；通用辅助保持小而有明确归属。
- 配置包含版本管理的安全样例，凭据与机器私人配置不入仓库。
- 开发、预览与正式游戏使用不同的记录命名空间。
- 新生成物有唯一生成入口，不再人工复制多个插件或播放器副本。

### 15.4 文件归属与变更管理

工程化不仅是分目录，还需要让“谁能改什么、改动影响什么”可解释。建议先定义职责，再由团队明确负责人，不在本方案里替任何人分配身份：

| 归属 | 应维护的契约 | 变更时必须说明 |
|---|---|---|
| 作品内容 | 文本、节点、变量、资源引用和演出意图 | 内容修订、受影响路线、是否影响旧存档 |
| 剧情运行 | 内容解释、状态转换和快照语义 | 接口及语义差异、转换需求 |
| 游戏表现 | 画面、声音、文字和输入体验 | 对演出等待、取消、恢复的影响 |
| 编辑工具 | 作者源编辑与预览回路 | 是否往返保留数据、是否影响 ID |
| 平台发行 | 宿主、资源装包、存储和生命周期 | 平台差异、系统要求、交付物 |
| 联网聊天 | 上下文、对话、供应能力及隐私 | 上传信息、费用或凭据要求、故障影响 |

协作规则建议保持轻量：

1. 一次任务写清目的、影响模块、接口或内容格式变化、交付结果和未完成项；不要制造第二份长期重复维护的待办总表。
2. 代码、内容和生成物有各自权威来源。生成物出现差异时修生成入口，不在发行副本上补丁叠补丁。
3. 跨模块修改先写清契约影响，再改消费者；不靠聊天里的口头约定长期维持兼容。
4. 非兼容内容、存档或编辑格式变化有简短决策记录，包含原因、替代方案和迁移影响。记录只在确有决策时创建，不为每个小函数建立流程。
5. 交付描述区分“已实现”“已接入”“待用户试用”“已验收”。文档存在、保存成功、构建成功和实际体验通过不是同一状态。
6. 小范围提交便于回退；不要夹带不相干素材、密钥、个人配置或未授权资料。是否推送、发布及启用工作流另行按授权处理。

这里不要求自动启动审查或测试任务，也不继承历史文档中的角色、分支和工作流安排。

### 15.5 诊断与性能记录

建议为内容构建、运行和宿主保留少量结构化诊断：

- 至少能定位作品、内容修订、节点 ID、当前阶段、步骤标识和错误类别。
- 区分内容错误、资源错误、存储错误、平台错误与聊天网络错误，避免统一显示“初始化失败”。
- 缺少必需剧情不能静默跳过；可选表现能否降级，要有明确策略和可见诊断。
- 调试日志不得默认输出凭据、完整聊天内容、私人路径或玩家整份存档；玩家导出诊断需要可理解的内容范围。
- 启动时间、内存峰值、图片和音频解码成本先观察当前目标设备，再定预算，不凭空承诺帧率和最低配置。

诊断的目标是回答“哪份内容、哪个步骤、哪个模块出了问题”，不是先建设复杂遥测平台；离线主线不应依赖上传日志。

| 被引用的专门文档 | 架构、格式、资源来源、决策、构建或发行细节 | 与入口重复维护另一套相互冲突的规则 |
| 规范维护约定 | 谁负责确认、何时同步、怎样废止过期内容 | 一次生成后永不更新 |

局部规范只在真实差异出现时建立。例如剧情核心的无 DOM／网络约束、内容工具的 ID 保留要求和原生宿主的环境要求，可以各有针对性说明；不要求给每个目录都生成一份文件。

需要明确根规则和局部规则各自的适用范围及冲突处理方式。局部规则不能擅自扩大任务授权、放松密钥与资源保护要求，或改变其他模块的权威来源。具体开发工具怎样发现和应用这些文件，要在正式采用时按团队实际使用工具确认，不能只凭文件存在就宣称所有工具都已正确接入。

本方案用当前绝对路径定位文件；将来团队规范的正文应以仓库位置、明确工作目录和可移植的命令说明为主，不写死某位成员的用户名、私人目录或本机安装位置。

### 16.3 必须覆盖的规则

以下是新规范的内容规格，不是要求把本表全文复制到根入口：

| 主题 | 必须说清楚 | 避免继续发生的问题 |
|---|---|---|
| 产品和任务边界 | 离线主线、独立编辑器、通关后聊天；区分调查、计划、实现和发布授权 | 把有限功能扩建成通用平台；写计划时顺手改代码 |
| 目录与文件归属 | 应用、共享模块、作者源、发行物、素材输入和运行数据分别在哪里 | 不知道改哪份文件；编辑生成副本 |
| 架构约束 | 唯一剧情核心、状态拥有者、依赖方向、公共接口与取消规则 | 全局变量互改、双解释器回落、循环依赖 |
| 内容与数据保护 | 节点和资源 ID、来源映射、音乐停奏、变量及存档兼容规则 | 工程调整无意改变作品或破坏存档 |
| 真实工程命令 | 已存在的开发、内容构建、类型检查和平台打包入口，工作目录、前置环境及适用范围 | 复制过期命令，或把尚未实现的脚本写成可用 |
| 改动与协作步骤 | 开工先了解工作区和改动范围，不覆盖他人未提交内容；跨模块说明契约影响 | 多人互相覆盖，大范围顺手修改 |
| Git 与发布 | 小范围提交、只纳入相关文件；推送、合并、发布、删资源和改写历史的授权边界 | 将完成实现误解成有权推送或发布 |
| 检查与验收 | 区分必需步骤、可选建议和当前未执行项；遵守当前用户的检查与交付要求 | 自动增加审查任务，或把没有运行的检查写成通过 |
| 安全与联网 | 不提交凭据，不上传私人资料；聊天配置不成为离线主线前置 | 泄露密钥，默认上传存档，联网故障阻断游戏 |
| 交付说明 | 改了什么、没有改什么、兼容影响、已做和未做事项、简短人工试用方法 | “保存成功”被写成“已验收” |
| 文档维护 | 命令、目录、接口或授权规则变化时同步入口；历史只读归档 | 入口再次变成过期交接记录堆 |

涉及验证命令时，要把“命令可用”与“每次任务都必须运行”分开。规范不能仅因列出了某个检查命令，就自动要求所有文档、素材或业务改动都执行它，更不能默认启动审查子代理。

按照用户目前明确的协作偏好，默认实现后直接交付并给出简短、具体的手动试用建议；额外测试、代码审查、独立复核和并行代理任务按当前任务授权开展。将来若要引入强制质量门禁，应先形成明确决定，再更新规范和工程入口，不靠历史文档暗中增加要求。

### 16.4 权威来源与防止规范膨胀

建议采用“短入口指向单一事实来源”的组织方式：

- `AGENTS.md` 说明怎样工作；架构文档解释模块和接口，术语表只定义领域用语。
- 格式规范记录内容与存档协议，构建说明记录真实命令，任务记录保存某次工作的结果。相同事实不在多份入口中手工复制。
- 当前分支、临时绕行、某天的工作进度和聊天摘要不写成永久规则。确有有效期的限制应说明范围、原因和解除条件。
- 团队角色和模块归属需要明确，但不从旧文档或提交作者推断当前负责人；人员和发布权限由团队确认。
- 旧规范只可作为待核对的历史材料，不默认继承其中的个人安排、分支名、命令和审批规则。新规范应从已确认约束及真实工程状态重建。
- 新规范经确认后要有一个明确有效的入口；旧入口及被替代的交接材料标注历史状态，不留下多个彼此声称“最新”的规范。
- 仓库规范不得被当成高于当前用户要求、工具约束或更高优先级指令的授权来源；发生冲突时说明冲突，不自行选择更宽权限。

根入口应保持足够简洁，让接手者无需先读一串历史会话就能定位任务。精简不能删掉关键约束，但也不能用篇幅和规则数量代替工程质量。

### 16.5 在迁移中的落地顺序

`AGENTS.md` 不应等重构完成后才补写，也不能在工程尚不存在时编造一套完整命令：

| 时点 | 计划交付 | 采用条件 |
|---|---|---|
| M0：基线与语义 | 规范范围、维护角色、最小根入口草案，区分现状和拟议目标 | 团队确认协作原则；不声称未来目录和命令已落地 |
| M1／M2：内容及核心开始落地 | 同步实际目录、内容构建和核心规则，按需要增加局部规范 | 相关文件和命令真实存在；状态与适用范围清楚 |
| M3／M4：表现与恢复 | 补充演出取消、快照、存档和内容兼容的协作约束 | 与实际接口一致，不另造规范专用规则 |
| M5／M6：平台与编辑器 | 补充两端环境、独立编辑预览和发行边界 | 平台差异及命令来源明确 |
| M7：收尾 | 收敛真实命令与入口，移除失效链接和过期规则，确认历史资料状态 | 新成员能够按规范完成一次范围清楚的任务 |

根规范初版是多人进入新工程前的协作交付；后续更新应尽量跟随引起变化的提交完成，而不是积压到最后一次集中“修文档”。

### 16.6 未来验收条件

以下是未来正式编写后的验收要求，本轮不执行演练、检查或额外审查：

1. **可定位**：新成员能从根入口找到任务所属模块、权威内容源及必要的专门文档，不必依赖口头交接。
2. **可执行**：列出的命令有真实工程入口、工作目录、环境和用途说明；未验证的环境明确标注，不编造成功记录。
3. **不越权**：仅要求调查或修改文档时，不会被规则引导去改业务代码、启动审查代理、推送或发布。
4. **不冲突**：根与局部规范的作用范围明确；同一事实只有一个维护来源，不出现互相要求覆盖的文件。
5. **能保护作品**：修改核心、内容、资源或存档时，能找到对应的 ID、语义、来源与兼容约束。
6. **能交付**：交付格式能区分实现、接入、试用和验收，说明未做事项，不把“没有报错”冒充完整验证。
7. **能维护**：有人或明确角色负责确认，命令及目录变化时有同步规则，失效规范有明确退出方式。

可以用“文档调整”“核心修改”“资源替换”三个代表任务做人工桌面演练，检查规范能否正确指导工作；是否开展及由谁确认，在该交付阶段明确，不默认新增自动化或代理审查。

### 16.7 维护责任

建议由团队指定一名协作规范维护责任人或角色，模块维护者负责局部事实。这里不指定姓名，也不默认维护责任人拥有所有发布或审批权限。

目录、命令、内容协议、平台流程或授权要求改变时，同步修改相应规则；规则本身的新增和放宽应说明原因及影响，不让单次任务中的临时方便变成永久授权。发现过期命令应报告不一致，不能凭猜测运行替代命令，再把猜测补进规范冒充已确认流程。

**完成标志是团队有可靠、简洁、与工程一致的协作入口，而不是生成了一份很长的 `AGENTS.md`。**

## 17. 构建与发行：一个内容产物，多个宿主封装

### 17.1 建议流水线

```text
作者源 + 资源来源记录
  → 结构与引用诊断
  → 规范化内容 + 来源映射 + 资源清单
  → 游戏前端发行物
  → Windows / Android 分别封装

编辑器 → 独立构建，不进入玩家发行链
聊天后端（如果需要）→ 独立部署，不进入离线主线前置链
```

构建不得依赖开发者当前目录中的碰巧残留文件、未记录的本地绝对路径或临时插件副本。两端需要消费同一内容修订，不能各自重新解释出不同剧情。

### 17.2 发行清单与资源归属

发行清单至少记录：

- 内容修订、构建来源和目标平台。
- 必要前端文件、剧情数据和资源文件。
- 资源 ID 到发行位置的映射及校验值。
- 缺失资源、替代资源、来源与授权信息的记录位置。
- 可选联网模块和外部运行依赖。

作者素材库、来源包、处理中间图、候选音频和最终游戏资源应有不同归属。可以保留原始大文件来源，不代表都打进游戏包；可以不进入发行物，也不代表允许删除。

不要在重构期间未经确认改写仓库历史或引入大规模资源迁移。资源分包、压缩、LFS 或外部存储需要根据实际体积和协作方式单独决定。

### 17.3 旧构建脚本的退出

现有试玩 HTML 和单文件构建脚本对作品文件及资源路径有自己的假设。新的前端发行物形成后，应逐项决定保留、改造或停用，不把它们继续复制旧文件的结果称为新版本发行物。

如果仍需要浏览器试玩或单文件展示，应把它视为独立交付目标，显式列出限制，不反向绑架 Windows、Android 的离线主线结构。

CI 的触发路径、资源收集和宿主入口需要一起更新。是否启用任何现有工作流是独立操作，不因为写出本方案而自动运行、恢复或删除。

### 20.2 值得以后自动化的少量高价值行为

如果后续授权引入自动化，优先围绕公开接口，而不是锁定内部函数：

1. 内容构建：重复 ID、悬空引用、表达式错误、空选择、缺失资源。
2. 剧情核心：相同输入序列相同结果，选择与超时只结算一次。
3. 快照：恢复不执行进入动作，回退恢复变量，非法快照不部分生效。
4. 游戏会话：旧步骤回调被拒绝，暂停计时正确。
5. 内容转换：关键节点、变量与资源映射不丢失。
6. 发行完整性：资源清单与实际打包一致，编辑器和凭据不进入游戏包。

用少量人工确认的固定样例作为对照，不盲目以旧实现每一个偶发现象为正确标准。旧 Rust/JS 的一致性检查也不能替代作品语义对照，因为两边可能共同缺少同一项能力。

### 21.2 进入实施前最值得先确认的四项

1. **重构首个切片的体验基线**：以现有作品外观和交互为基准，还是同时批准具体体验调整。建议先保持现状，不夹带改版。
2. **旧存档承诺**：明确不兼容、尽力一次性迁移，还是必须支持某些发布版本。建议先限定支持范围，而不是无限兼容。
3. **界面框架选择**：结合团队经验决定即可，不应改变唯一核心和编辑器独立的总体结构。可以先做无框架绑定的核心和内容工具。
4. **协作规范的采用与维护责任**：确认根入口的采用方式、维护角色和局部规则范围。将其放到多人进入新工程之前，不推迟到代码重构结束。

模型供应、聊天长期记忆和分发商店可以稍后决定，不能以这些未定事项为由阻塞内容语义和核心整理。

### 21.3 方案完成与重构完成不是一回事

本文件可以作为后续讨论和任务拆分的基线。真正的重构完成需要至少满足：

- Windows、Android 的完整离线主线及恢复行为按约定验收。

- 旧链路的保留、退出和来源归档有明确理由。
- 发行物能追溯到代码和内容，不依赖开发者本地残留。
